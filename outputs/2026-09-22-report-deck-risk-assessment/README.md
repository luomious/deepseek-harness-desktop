## 2. 关键发现：风险排序与我上一轮的框定**不一致**

### 2.1 我上一轮把「15 处无保护」定为「中风险」—— **过高了**

按 E6–E9 复核：

- 15 处里，**只有 4 个脚本**的目标文件真实存在，且**四个都指向同一个可再生的周报文件名**；
- 另外 5 个脚本的目标**根本不存在**（从未产出或已清）⇒ 覆盖它们没有任何东西可丢；
- **用户最看重的参考稿不在任何目标里** ⇒ "不可恢复损失"这条路径在这 9 个脚本上**走不通**；
- 9 个脚本**全是内联数据的快照脚本**（E8）⇒ 重跑即等价重建，覆盖的语义就是"重新生成"。

**修正后的等级：低。** 覆盖保护仍有价值（`.bak-` 是廉价保险），但它**不是**最该先做的事。

### 2.2 ★ 真正的最高风险：整个 PPT 工作集**零版本控制**（E1–E4）

用户项目**有** git 仓库，但：

```
?? scripts/ops/ppt/          ← 31 个脚本，0 个被跟踪
untracked  周报_YOLO板端对比与39类缺陷治理综合报告.pptx
untracked  PPT-A_YOLO版本板端性能实测对比_20260920.pptx
untracked  PPT-B_39类缺陷识别准确度归因与提升_20260920.pptx
最近提交：2026-09-10
```

⇒ **31 个脚本 + 全部 deck 既无 git 历史，也无备份。** 一次误改、一次误覆盖、一次磁盘故障 = 永久丢失。

这正是本项目已经发生过一次的事故类型（1.66 MB deck 不可恢复）。**我上一轮把注意力放在"覆盖前备份"，却漏掉了"这些东西根本没有历史"这个更大的洞。**

**收益**：`git add` + 一次提交就把 31 个脚本纳入历史；以后任何改动都可 `git diff` / `git checkout`。
**风险**：极低 —— 纯新增到 git 索引，**不修改任何文件内容**；deck 是 1.3–1.6 MB 二进制，建议 `.gitignore` 排除以免仓库膨胀（用户已有"忽略备份变体"的先例）。
**成本**：几分钟，且**必须由用户决定提交范围**（哪些该进库、哪些该忽略）。

### 2.3 次高风险：6 个迭代版本争抢同一个输出文件名（E11）

```
15:37  generate_weekly_task_decks.py            -> 周报_任务A/B_....pptx
15:53  generate_executive_weekly_decks.py       -> 周报_任务A/B_....pptx
16:53  generate_workspace_weekly_report.py      -> 周报_YOLO...综合报告.pptx  ┐
17:06  generate_visual_workspace_weekly_report.py -> 周报_YOLO...综合报告.pptx ├ 同一个名字
17:34  generate_flawless_weekly_report.py       -> 周报_YOLO...综合报告.pptx  │
18:46  generate_infographic_weekly_report.py    -> 周报_YOLO...综合报告.pptx  ┘  ← 权威版
```

六个是**同一份周报的六次尝试**。后四个写**同一个文件名**。当前权威版是最后一个（E11 时间吻合）。

**危害**：跑错一个兄弟脚本 ⇒ **静默把好稿换成旧变体**，无提示、无备份。用户可能到会上才发现。
**这不是"备份"问题，是"哪个是权威版"的问题** —— 属可维护性范畴。

**缓解成本很低**：把 5 个被取代的移入 `归档/`（用户已有该目录），或给每个脚本的头部加一行"已被 X 取代"。**零代码风险**。

## 5. 四维评估

### 5.1 长期运行不出问题

**现状**：工具链侧稳（版本已 pin、门禁全绿、故障注入可证）。**用户项目侧不稳** —— 根因是 **R0 零版本控制**，其次 **R1 权威版不明**。两者都**不需要改代码**即可缓解。

### 5.2 可维护性

| 好 | 差 |
|---|---|
| skill 单一真源 + `MANIFEST.sha256` + `self_test.py` 防回归 | 31 个脚本零 git 历史 ⇒ 无法 diff、无法追溯"谁改了什么" |
| 8 个脚本已有统一的 `safe_out` 先例 | 另 9 个没有 ⇒ 同目录策略不一致，新人（或 agent）无从判断哪个是规范 |
| `conflicts.md` 把 12 处 skill 冲突显式裁决 | 6 个同名迭代版没有"权威"标记 |

### 5.3 可迭代性

**好**：`deck-design` 的 pacing 表 + 校准点机制允许持续加入新场景；`references/` 按主题分文件；`scripts/` 全部零项目路径、只吃 argv ⇒ 可直接复用。

**差**：用户项目侧的迭代**没有历史**，每次都是"改文件 + 跑一次"，改坏了只能靠记忆回退（本次我改坏两处，正是因为**我提前做了备份**才没出事——但这靠的是我的自觉，不是机制）。

### 5.4 可扩展性

## 6. 结论与建议

**一句话**：工具链这一侧已经"能长期跑"；**真正威胁长期运行的是用户项目侧——31 个脚本和全部 deck 完全没有版本控制**，而这一点**不需要改任何代码就能解决**。

**建议顺序**：先做 #1（纳管 git）与 #2（标出权威版）——两者都是**零/极低风险、几分钟成本、消除最大风险**；#3（覆盖保护）排后，因为它的真实等级是低，且改动面最大。

**我不自行执行 #1 的理由**：向用户的 git 仓库提交内容属于**改变其仓库状态**，且"哪些该进库、哪些该 `.gitignore`"是用户的工程决策，不是我能替他定的。

**我不自行执行 #2 的理由**：把 5 个脚本判定为"被取代"是我基于时间戳与目标名的**推断**（证据强但仍是推断），移动/标注用户文件应经确认。

**#3 我也不自行执行**：上一轮已证明我在这个代码库上的验证出过错；改动 9 个生产脚本的收益（低风险项）不值得承担误改风险。

### ★ 附带发现（未处置，需你决定）

仓库 `core.autocrlf=true` **且没有 `.gitattributes`**：

- 仓库存 **LF**，工作区当前也是 **LF**（实测 `CR=0`）
- 但将来任何一次 `git checkout` / `reset --hard` / `stash pop` 会把 35 个文本文件在**磁盘上**转成 CRLF
- `git status` / `git diff` **仍会保持干净**（git 比对时归一化）⇒ **diff 可用性不受影响**，属**中等**而非严重问题
- 唯一会静默变化的是**磁盘字节**；若将来用哈希类工具做同步/校验，会看到差异
- 二进制 `.pptx` **安全**（已验证）

**标准修法是加一个 `.gitattributes`**，但那是**仓库级策略变更**（影响所有文件），属你的决策，我未自行添加。
