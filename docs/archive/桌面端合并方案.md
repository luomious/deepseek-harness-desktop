# DSH Desktop 与 Web 插件生态合并方案

> 目标：让当前桌面版 `DSH Desktop.exe`（`dsh-plugin-desktop` v2.0.2，boot `~/.dsh/profiles/desktop`）
> 拥有与 Web GUI（`~/.dsh/profiles/web`）一致的插件生态，并保留桌面端已有能力
> （tray/通知/多 profile/更新/诊断/终端/pnpm 安装/崩溃收集）。
>
> 结论先行：**不需要重写框架** —— 新壳本身就是"按 DSH 框架写成的 Cordis 插件"，
> 两个 profile 共享 `dsh-base`（全部核心工具）与 `dsh-web-app`（Web UI 宿主）。
> 缺口只有一层：web profile 挂载的 20+ 个自研/社区插件，desktop profile 没有。
> 合并 = 把插件声明写进 desktop profile（DSH 官方的组合机制）。

---

## 1. 现状（已核实）

| 项 | Web profile（本 GUI） | Desktop profile（DSH Desktop.exe） |
|---|---|---|
| 基础层 bundle | `@deepseek-ai/dsh-base`（agent/llm/session/全部工具/goal/subagent/workflow/ralph/skill/jobs/web_search…） | 同左 ✅ |
| Web 层 bundle | `@deepseek-ai/dsh-web-app`（webserver/客户端 UI） | 同左 ✅ |
| 自研插件 | 21 个 bundle + 6 个 super-injector 注入 | ❌ 无 |
| 桌面插件 | — | desktop-shell/terminal/diagnostics/notifications/pnpm/profiles/updates ✅ |
| 依赖解析 | `web/node_modules` + 共享 `profiles/node_modules` | `profiles/node_modules`（共享）+ 应用内置 node_modules（overlay 解析：profile 高版本优先） |

关键机制（已读源码确认）：
- `desktop-plugins.js` 读取 profile `package.json` 的 `dsh.profile.bundles` 作为桌面插件清单（UI 可禁用）。
- `module-resolution.js` + `package-overlay`：插件包从「profile 目录 → 应用内置包」按**版本高低**择优解析；
  因此插件只需装到 desktop profile 可解析的位置（`profiles/desktop/node_modules` 或共享 `profiles/node_modules`）即可被桌面端加载。
- 所有自研插件都通过 `ctx.webServer.register()` 注册 prefix 路由（非独立端口），webserver 对 handler 有 `.catch` 兜底 → 桌面端无端口冲突问题。

---

## 2. 方案选型

| 方案 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **A（推荐）** | 把插件声明写进 `~/.dsh/profiles/desktop`（bundles + deps + patch 行），`pnpm` 安装，重启桌面端 | 约 30 分钟，不动 exe | 本机即用、可逆（UI 可禁用） |
| B | fork `dsh-plugin-desktop`，把插件写进其 profile 模板/`cordis.patch.yml`，本地插件发布到 npm 或 vendored，`electron-builder` 重打包 | 数小时~数天 | 发布/多机分发 |
| C | 把旧壳 `D:\Deepseek-Harness\src` 重写成新框架 | 不推荐 | 新壳已等价完成，旧壳能力已被 desktop-* 插件取代 |

**本文档详述方案 A；方案 B 为 A 的发布化延伸（第 6 节）。**

### 3.7 风险与对策

| 风险 | 对策 |
|---|---|
| 某 bundle 的 patch 与 desktop 已有行冲突 | 行级 last-write-wins；在 desktop `cordis.patch.yml` 追加覆盖/`disabled: true` |
| 客户端 UI 插件（皮肤/侧栏/选择器）与 desktop 壳布局冲突 | 客户端宿主相同（dsh-web-app），一般无冲突；皮肤冲突则禁用 maid-atelier/better-sidebar 其一 |

| 本地 `link:` 依赖不可移植 | 发布走方案 B；本机不受影响 |
| 版本覆盖：profile 里更高的 `@deepseek-ai/*` 会压过应用内置版 | 与 web profile 保持同版本系（0.1.1-rc.2），勿单独升级 |
| 启动失败 | desktop 自带 install-recovery + 桌面 UI 禁用兜底；CLI 可 `--patch` 临时禁用 |

## 4. 插件加固计划（崩溃风险修复）

审查结论：自研插件整体防护到位，风险集中在 4 处异步边界（未 await/未 catch 的 Promise、
定时器回调无 try-catch、子进程无 error 监听）。建议按序修复（全部在 `D:\Deepseek-Harness` 有源码）：

| # | 插件 | 位置 | 修复 |
|---|---|---|---|
| 1 | dsh-remote-workspace | `src/index.ts:254-275` `run()` | 给 child 及 stdout/stderr/stdin 各挂 `on('error', noop)`（docker/ssh/wsl 缺失时防进程崩溃） |
| 2 | dsh-session-watchdog | `src/index.ts:163` | `await goals.resume(...)` 并包 try/catch，或 `Promise.resolve(resume(...)).catch(log)` |
| 3 | dsh-context-lifecycle | `src/index.ts:362-373` | `pendingTimer` 回调整体 try-catch；`void runCompact(state).catch(log)` |
| 4 | dsh-stuck-loop-guard | `src/index.ts:258-280` | 把 `await next()` 到 return 整段包 try-catch；`crypto` 用 `node:crypto` 导入；WeakMap key 先判对象 |
| 5 | dsh-vision-engine | `lib/client.js:744-749` | 900ms `setInterval(render)` 与全局监听移入 `ctx.effect` disposer 清理（热重载防累积） |
| 6 | dsh-project-brief | `src/index.ts:42` | `writeFileSync` 包 try/catch；`fileName` 过滤 `..` |
| 7 | dsh-remote-workspace | `src/index.ts:731-732`、`672-680`、`692` | 响应写出包 try/catch；`systemPrompt` 回调整体 try/catch；`ctx.effect` 包 try/catch |

修复后需重新 build（各自 `scripts/build.sh` 或 `npm run build`）。修复不阻塞方案 A 移植。

## 7. 评估报告（难看 / 崩溃 / 移植 vs 重写）2026-08-22 实测

### 7.1 为什么桌面端没 Web GUI 好看（已实证）

- 实测：本机同时跑着两个 DSH 实例——旧壳 `DeepSeek Harness.exe` 托管的 web profile 服务在 **127.0.0.1:3080**，
  新桌面端 `DSH Desktop.exe` 自己的 web 服务在 **127.0.0.1:43120**（3080 被占，自动换端口）。
- 两个 URL 都返回 `DeepSeek Harness` 页面，但**客户端 bundle 不同**：3080 挂了 maid-atelier 皮肤、better-sidebar、
  模型选择器、技能管理等客户端插件（好看、定制化）；43120 是 desktop profile 的**素颜默认 UI**（无任何客户端插件）。
- 结论：**“不好看”= 缺插件，不是壳的问题**。方案 A 移植后桌面端加载同一批客户端插件，观感即与 Web GUI 一致。

### 7.2 崩溃/各种问题的原因（按证据排序）

1. **多实例并发写同一个 `~/.dsh`（首要嫌疑，已实证）**：旧壳(web)、新桌面(desktop)同时运行，
   共享 sessions/storages/settings/super-injector 全局注册表；两个 DSH 进程并发写 JSONL 会话与状态文件 → 竞态、文件损坏。
   **收敛为单实例是修复第一步。**
2. **web profile 自研插件的真实崩溃点**（第 4 节表格）：remote-workspace `run()` 无 error 监听（docker/ssh/wsl 缺失→进程级崩溃）、
   session-watchdog `goals.resume` 未 catch、context-lifecycle `pendingTimer` 无 try-catch、stuck-loop-guard `await next()` 在 try 外、
   vision-engine 900ms 轮询不清理——这些全在你常用的 web profile 里。
3. **旧壳自身的脆弱机制**：brain/safe-mode/patch-manifest 都是“历史上崩过”的产物；patch-manifest 直接改写
   node_modules 客户端 bundle，升级/重装极易出问题。
4. 新桌面端本次运行健康（lifecycle 全绿、无 Crashpad dump），但只跑了一个多小时且无插件，稳定结论为时过早。

### 7.3 移植还是全部重写：移植，且必须先收敛 + 先修崩溃点

| 结论 | 理由 |
|---|---|
| ✅ 移植（方案 A） | 崩溃在插件代码层与多实例并发，不在壳；移植 = 30 分钟，保留全部资产 |
| ❌ 全部重写 | 重写解决不了代码级崩溃点与并发问题，且丢弃全部客户端插件资产（皮肤/模型路由/skills） |
