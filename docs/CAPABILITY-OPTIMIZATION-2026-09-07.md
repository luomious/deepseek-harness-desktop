## 一、安全性

### 1.1 我的优点（可迁移）

| 优点 | 具体表现 |
|---|---|
| **fail-closed 思维** | 校验失败一律阻断，不降级放行（DSH 官方 skill 规范本身也是这个设计） |
| **故障注入验证** | 写完防护必须故意弄坏一次证明有效（已沉淀为 skill） |
| **纵深防御** | 不依赖单点（网络层+应用层+数据层各自设防） |
| **证据驱动审计** | 每个风险带 `路径:行号`，不写无证据结论 |

### 1.2 DSH 现状

| 项 | 状态 | 证据 |
|---|---|---|
| 壳层安全基线 | ★★★★★ 全 sandbox/contextIsolation/loopback 三层强制 | 审计 §4.1 |
| 命令风险拦截 | 有 `dsh-command-guard`，但**无默认 allowlist** | 审计 §4.2 M2 |
| 依赖漏洞扫描 | **无**（`adm-zip` 等有历史问题） | 审计 §4.2 L2 |
| 安全审计流程 | **无例行** | — |
| **已有但未启用** | `dsh-skills-hub` 里有 **`security-audit`**、**`dep-auditor`** 两个现成 skill | `tools/dsh-skills-hub/skills/` |

### 1.3 优化建议

| 优先级 | 项 | 做法 |
|---|---|---|
| **P0** | **启用 `security-audit` + `dep-auditor` skill** | 从本地 hub 安装到 `~/.dsh/skills`（无需联网下载，本地有源码）|
| **P0** | 命令白名单默认启用 | `dsh-command-guard` 从评分告警升级为白名单拦截（先观察期仅告警） |
| **P1** | 依赖漏洞例行扫描 | `dep-auditor` + 接入升级日流程；单机模式下建议**每月一次**而非 CI 每次 |
| **P1** | 建立"安全变更清单" | 涉及鉴权/沙箱/凭据的改动，走强制复核（可做成 skill） |
| **P2** | `runAsNode` 熔断改造 | 单机威胁模型下收益有限，**维持登记为已知风险**（方案书附录 D 已列） |

> **单机定位下的取舍**：不需要企业级 SDL。重点放在"**别自己把自己搞坏**"（误删、误改配置、误升级），
> 而非"防外部攻击者"。因此白名单和依赖扫描优先，渗透测试类不做。

## 四、画图（**当前最大痛点**）

### 4.1 现状诊断

`dsh-diagram-renderer` 迭代史暴露了一个结构性问题：

| 版本 | 做法 | 结果 |
|---|---|---|
| v6.4 | keyed 工具节点单通道 | 失败（turnTail 退役，关闭了唯一可见通道） |
| v6.5 | 恢复 turnTail 主通道 + 历史信封扫描 | 修复 |
| v8 | **React fiber 直读 envelope + DOM 直渲染**，绕过 conversationEvents | 再次绕过 |

**根因**：该插件一直在**依赖 DSH 宿主的内部渲染通道**（turnTail / keyed slot / React fiber 内部结构）。
宿主一变就失效 —— 这解释了为什么几个月内反复翻修。

### 4.2 我的优点（本助手）

| 优点 | 具体表现 |
|---|---|
| **自包含渲染** | 输出独立 SVG/HTML，**不依赖宿主 DOM 注入**，刷新/归档/分享都不失效 |
| **多形态** | SVG 图、Chart.js 图表、交互式 HTML、架构图、流程图 |
| **主题自适应** | 跟随 IDE 明暗主题，不在深色主题下出黑底黑字 |
| **轻量** | 内联渲染，无构建、无缓存陷阱 |

### 4.3 优化建议（**重点**）

| 优先级 | 项 | 做法 |
|---|---|---|
| **P0** | **增加"独立 artifact"后备通道** | diagram 工具除交互卡外，**同时输出一个自包含 `.svg`/`.html` 文件**到 `diagrams/`。即使宿主通道失效，图仍在文件里 |
| **P0** | **降低对 React fiber 的依赖** | v8 的 fiber 直读是脆弱方案（依赖 React 内部结构，升级即碎）。建议回到官方事件/插槽 API，或明确标注为"临时方案 + 有后备" |
| **P0** | 启用 `diagram-design` skill | hub 里有，**52 种图表类型**的规范（架构/流程/序列/状态/ER/时间线/泳道/象限） |
| **P1** | 图表资产归档规范 | `diagrams/` 已有 13 个文件，加命名规范 + 索引（当前 8 个 SVG 有 4 个是同名不同时间戳，易混淆） |
| **P1** | 双通道输出标准化 | 定义：交互卡（会话内看）+ 独立文件（可归档/分享），两者同源 |
| **P2** | 主题与尺寸规范 | 参照 `diagram-design` skill 的规范统一配色/尺寸/字号 |

> **一句话**：画图的稳定性问题，本质是"把渲染绑在宿主内部结构上"。
> 我的做法是**自包含 + 不依赖宿主**——这是可以直接借鉴的架构改进，不只是工具层面。

| **P2** | 3D 生成 | 单机工业场景需求低，**暂不做**（登记为可选） |

> **单机定位下的取舍**：图像/视频生成依赖云端 API，与"离线优先"有张力。
> 建议做成**按需 skill**（用时才联网），而不是常驻插件——符合升级日开窗的原则。

## 六、重叠与取舍（诚实说明）

我新建的 6 个方法论 skill 与 hub 里已有的存在**部分重叠**：

| 我建的 | hub 已有 | 重叠度 | 建议 |
|---|---|---|---|
| `subagent-orchestration` | `dispatching-parallel-agents` + `subagent-driven-development` | **高** | 我的是"何时派/如何切分/如何综合"的**决策层**；hub 的是**执行层**方法论。可并存，但需在 description 里明确区分，避免模型加载两份 |
| `verify-by-fault-injection` | `verification-before-completion` | **中** | 我的是"故意弄坏验证防护有效"；hub 的是"完成前验证"。**互补**，保留 |
| `evidence-driven-audit` | `security-audit` | 低（后者是安全专项） | 保留 |
| `parallel-execution` | 无直接对应 | — | 保留 |
| `falsification-check` | 无直接对应 | — | 保留 |
| `multi-step-tracking` | `executing-plans` / `writing-plans` | 中 | 我的是"任务清单粒度"；hub 的是"计划执行"。可并存 |

**处理建议**：不急着删。先让两套共存一个周期，观察实际触发情况，再按"哪个被真正加载"决定去留。
这符合"**不为了整洁而牺牲可用性**"——单机系统里，可用性 > 纯洁性。

## 七、落地优先级（建议顺序）

| 波次 | 内容 | 理由 |
|---|---|---|
| **第 1 波**（低风险/高收益） | 从本地 hub 安装 **10-15 个高频 skill**：<br>`diagram-design`、`docx`、`pptx`、`xlsx`、`pdf`、`security-audit`、`dep-auditor`、`dispatching-parallel-agents`、`verification-before-completion`、`zh-docgen`、`web-artifacts-builder` | 本地有源码，**零网络依赖**；直接补上画图/生成/安全三大缺口 |

| **第 5 波**（可选） | 图像/视频生成 skill（需外部 API） | 与离线优先有张力，按需做 |
