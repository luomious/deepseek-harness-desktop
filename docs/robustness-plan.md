# DSH 桌面端鲁棒性改造方案（问题清单 + 可行性分析 + 分阶段实施）

> 状态：**已实施完成（v1.3.0，2026-08-18）**——阶段 0~4 全部落地，成功指标实测达标，见文末「实测验证记录」
> 背景：近期连续出现 rc.7 空壳崩溃、modlens 卡片消失、package.json BOM 启动卡死等问题，每次都是「报错 → 人工定位 → 手动修复」，重复劳动且无系统兜底。本文给出整体改造方案与分阶段实施计划，先验证可行性再逐步完善。

---

## 1. 目标

| 目标 | 对应能力 |
|------|----------|
| 报错可定位 | 统一诊断中心（错误码 + 结构化日志 + 一键导出） |
| 报错不致命 | 熔断 + 安全模式 + 模块隔离 + 崩溃自动恢复 |
| 报错不重复 | 错误码→解决方案映射、补丁自愈清单、打包自动冒烟 |
| 代码可维护 | main.js 模块化拆分、冗余收敛 |
| 打包不翻车 | 打包后自动启动验证 + verify 扩展 |

## 3. 方案设计

### 3.1 诊断中心（src/main/error-log.js + error-codes.js）

- **统一日志**：JSON 行式追加（`ts|level|module|code|msg|stack|ctx`），按大小轮转（复用现有截半机制，上限 1MB/文件）
- **错误码体系**（草案见附录）：
  - `BOOT-0xx` 启动类（服务启动失败/端口占用/超时）
  - `RENDER-0xx` 渲染类（崩溃/无响应/导航拦截）
  - `PLG-0xx` 插件类（加载失败/注册冲突/slot 未声明）
  - `NPM-0xx` 依赖类（npm/pnpm 操作失败）
  - 每个错误码挂「解决指引」（中文，直接写进日志文件），日志即手册
- **服务端日志落盘**：dsh 进程 stdout/stderr 追加到 `dsh-service.log`（行式截半），运行中报错不再丢失
- **一键导出诊断包**：菜单「导出诊断报告」→ 收集（启动/渲染/错误/服务日志 + 应用/DSH 版本 + 插件列表 + asar 指纹）→ 打包 zip

### 3.2 安全机制（src/main/safety.js）

- **熔断 + 安全模式**：
  - 状态文件 `~/.dsh/profiles/web/.dsh-state.json` 记录连续启动失败次数
  - 连续失败 ≥3 次 → 下次启动进入安全模式：只加载核心 bundle（dsh-base/dsh-web-app）、跳过全部第三方插件，启动成功则重置计数
  - 避免「插件搞挂 → 反复重启 → 反复挂」的死循环；用户手动重启（勾选）不计数
- **崩溃自动恢复**：`render-process-gone` → 记录 → 延迟 5s reload（限 3 次/小时，超限进安全模式）
- **服务看门狗**：服务启动超时 → 杀端口 → 重启一次（带计数，防无限循环）
- **execSync 根治**：npm 查询改异步 spawn + 超时强杀；或静态路径优先 + 结果文件缓存（`%TEMP%\dsh-npm-paths.json`），彻底摆脱 Windows timeout 不可靠问题

### 3.3 模块化重构（src/main/ 目录）

```
src/main/
  index.js          入口（组装 + 生命周期，约 50 行）
  logger.js         日志统一（启动/渲染/服务/错误）
  error-log.js      错误记录 + 错误码映射
  error-codes.js    错误码 → 解决指引表
  dsh-service.js    服务生命周期 + 看门狗（startDSH/stopDSH/waitForDSH/端口自愈）
  plugin-manager.js 插件管理（list/install/uninstall/enable/reconcile）
  safety.js         熔断/安全模式/崩溃恢复
  window.js         窗口创建 + 导航拦截 + 前端日志挂接
  update.js         更新检查/执行（checkForUpdates/performUpdate）
  ipc.js            IPC 注册
  utils.js          execNode/execSyncSafe/端口/工具
  lib/npm-paths.js  npm prefix/root 查询（唯一实现 + 缓存）
```

- 纯 CJS 拆分，无新依赖；asar 打包自动包含子目录（已验证 `lib/version.js` 可正常 require）
- 错误日志带模块名 → 一行定位问题模块；各模块可独立单测

### 3.4 冗余收敛（阶段 1，改动最小）

- `execSyncSafe`、npm prefix/root 查询、QClaw 兜底路径 → 全部收敛到 `lib/npm-paths.js`，main.js 与 patch-dsh-native-picker.js 共用
- 预计 main.js 净减 100+ 行，消除两处实现不一致风险

### 3.5 插件健壮性（面向"后续再开发插件"）

- **补丁自愈清单 `patch-manifest.json`**：登记所有 node_modules 补丁点（文件路径 + 补丁后指纹），启动时校验，被 dsh 升级覆盖 → 自动重打（现有 applyNativePickerPatch 扩展为清单化）
- **插件兼容检查**：启动时扫描各插件注册的 slot id（keyed slot 是否带 key、是否已声明），冲突/违规 → 记 `PLG-0xx` + 该插件跳过加载，不再崩全局
- **插件开发规范（写入文档）**：keyed slot 必须带 `key`；注册前先 `settings.describe` 查服务名单；不依赖未声明 slot；改动 node_modules 必须登记 patch-manifest
- **版本策略**：建议锁定 dsh 版本（不追 rc 小版本），升级前先跑插件兼容检查

### 3.7 智能诊断引擎（src/main/brain.js + loop-detect.js）——「大脑」

用户核心诉求：不是机械的规则匹配，而是**感知 → 判断 → 决策 → 执行 → 学习**的闭环，能识别问题、判断怎么处理、评估每一步对系统的影响、并防止死循环。

```
                感知层                    诊断层                  决策层                  执行层
  错误事件/状态快照 ──► 指纹提取+模式识别 ──► 回环检测+影响评估 ──► 动作库(节流+幂等) ──► 反馈回写(学习)
        ▲                                                                                 │
        └──────────────────────── 经验表 .dsh-brain.json（成功/失败计数，下次优先）◄────────┘
```

**3.7.1 感知层（统一事件入口）**
- `brain.emit(event)`：所有错误/异常（error-log 的每个错误码、渲染崩溃、服务退出、端口占用）都作为一个事件进入引擎
- 事件结构：`{ code, module, stage, key(指纹参数), ts }`

**3.7.2 诊断层（指纹 + 模式识别）**
- **错误指纹**：`errorFingerprint = 错误码 + 阶段 + 关键参数`（如 `BOOT-004|wait|`、`PLG-001|modlens`）——同类问题归并，不重复处理
- 规则表：指纹 → 候选动作列表（按破坏等级升序）

**3.7.3 回环检测器（loop-detect.js）——防死循环核心**
- 维护最近事件链（20 条，含动作记录）
- **判环算法**：滑动窗口内检测「动作 → 同指纹错误 → 同动作 → 同指纹错误」的周期模式（同指纹连续失败 ≥2 次且伴随动作）→ 判定为环
- 判定为环 → **停止当前策略** → 升级到下一破坏等级（见下）→ 继续观察；再成环 → 再升级 → 直到安全模式（终态，不再自动动作，仅通知用户）
- 因此**任何循环最多触发有限次动作**，不存在无限重试

**3.7.4 决策层（带影响评估）**
每个动作带影响元数据，决策时从低破坏往高破坏尝试：

| 等级 | 动作 | 影响范围 | 破坏性 | 说明 |
|------|------|----------|--------|------|
| 0 | retry（重试） | 无 | 无 | 重试/等待后再查 |
| 1 | restart（重启服务） | dsh 服务 | 低（会话中断） | 端口自愈后重启 |
| 2 | kill-port（杀端口进程） | 占用进程 | 中（白名单 node/electron 才杀） | 已有 killProcessOnPort |
| 3 | skip-plugin（跳过插件加载） | 单个插件 | 中 | 插件级隔离 |
| 4 | safe-mode（安全模式） | 全部第三方插件 | 高（降级功能） | 终态 |
| 5 | notify（仅通知用户） | 无 | 无 | 人工决策 |

- 每个动作执行前记录**预期影响**，执行后记录**实际结果** → 写入经验表
- **节流**：同指纹同动作 ≤1 次/10 分钟；全局自动动作 ≤10 次/小时（超限只记录不动作）

**3.7.5 学习层（.dsh-brain.json 经验表）**
- 指纹 → 各动作的成功/失败计数（如 `BOOT-004 → {restart: 成功3/失败0, kill-port: 成功1/失败1}`）
- 下次同指纹优先选成功率高且等级低的动作；连续失败的动作降权
- 效果：**同类问题第二次起处理更快更准**（「重复报错每次修太麻烦」→ 引擎自动处理 + 日志给出结论）

### 3.8 QClaw 兜底路径清理

- 代码中 QClaw（`AppData\Roaming\QClaw\npm-global`）出现 6 处，全部是 dsh/bin/pnpm/npm 的**兜底候选路径**——QClaw 是 DeepSeek 官方 CLI 发行版，历史上通过它分发 dsh
- **已验证当前机器无 QClaw 目录**（dsh 实际位于 `Roaming\npm`），这些候选永不命中 → 纯冗余
- 处理：阶段 1 收敛到 `lib/npm-paths.js` 时**移除全部 QClaw 候选**（保留注释说明历史用途）

### 3.6 打包 / 更新机制

- **打包后自动冒烟**：build-app.ps1 尾部加「启动 exe → 等 3080 就绪 → 查启动日志无错误 → 自动退出」；坏包（BOM 这类）当场拦截
- **verify 扩展**（已部分完成）：BOM 检查 / JSON 可解析 / 关键标记 / lib/version.js 存在 / 打包后启动验证
- **asar 与 src 同步**：post-commit hook 已存在（asar 过期提醒），保留
- **长期（对外发布时）**：electron-builder + autoUpdater 正式安装包方案，另行立项

## 4. 分阶段实施计划（每阶段含验收标准）

### 阶段 0：可行性验证（先证后建）

**第一步（最小闭环，独立新文件，不碰 main.js，零回归风险）**：搭建诊断引擎骨架 `src/lib/brain.js` + `src/lib/loop-detect.js` + 测试 `tests/brain-logic.js`，用**模拟事件流**验证核心逻辑：
- 注入 [BOOT-004 → restart → BOOT-004 → restart] 环 → 引擎第 2 轮判环并升级动作（停止 restart 改 kill-port）
- 注入单次错误 → 引擎按破坏等级选最低动作，并记录「预期影响 vs 实际结果」
- 验证节流：同指纹第 4 次不再自动动作、全局 10 次/小时上限生效
- 验收：全部用例通过 → 引擎逻辑成立 → 进入 V1-V3 及真实信号接入

- V1 模块化可行性：把 `execSyncSafe`/npm 路径查询抽到 `lib/npm-paths.js`（main.js 与 patch 共用，同时移除 QClaw 候选），跑 `tests/smoke-v119-logic.js` + 手动启动回归（窗口/3080/插件卡片/设置页）
- V2 熔断可行性：实现最小熔断（启动失败计数 + 安全模式跳过 bundle），故意破坏一个插件验证「进安全模式 + 基础功能可用」
- V3 错误日志可行性：手动触发一条错误 → 确认 JSON 行格式可读、错误码带解决指引
- **验收**：三项验证通过 → 进入阶段 1；任一不通过 → 调整方案再验

### 阶段 1：低风险快速项（半天）
- 冗余收敛（3.4）、服务端 stderr 落盘、打包自动冒烟
- **验收**：`npm test` 通过、启动回归通过、打包冒烟能拦截坏包（拿旧 BOM 包反测）

### 阶段 2：诊断中心（1 天）
- error-log.js / error-codes.js / 导出诊断包 / 菜单入口
- **验收**：注入 3 类错误（启动失败/渲染崩溃/插件失败）→ 日志均有结构化记录 + 解决指引；导出 zip 可用

### 阶段 3：模块化重构（1-2 天）
- main.js 按 3.3 拆分，行为等价重构
- **验收**：全部功能回归（启动/更新/插件管理/远程面板/设置）+ 测试通过 + 错误日志带模块名

### 阶段 4：安全机制 + 补丁自愈（1-2 天）
- safety.js（熔断/恢复/看门狗）+ patch-manifest
- **验收**：故意破坏插件 → 安全模式启动且基础功能可用；崩溃自动恢复生效；升级 dsh 后补丁自动重打

## 5. 可行性分析

| 维度 | 结论 |
|------|------|
| 技术 | CJS 模块化、JSON 日志、spawn 超时——均无新依赖；asar 打包已支持子目录与 require（lib/version.js 实证） |
| 回归风险 | 阶段 1 只收敛不改行为；阶段 3 重构后用现有测试 + 启动回归表兜底；熔断误判通过「手动重启不计数」规避 |
| 日志增长 | 截半机制（1MB 上限）已有，行式 JSON 同样适用 |
| 效果度量 | 修复平均耗时下降（错误码直查）、同类错误复发率（自愈清单）、启动成功率、插件故障自恢复率 |

## 6. 成功指标

- 连续 10 次启动成功率 100%，无手动干预 → ✅ **实测 20/20（两轮 10 次），平均 3.3~3.5s**
- 注入插件错误 → 安全模式启动，基础功能可用，日志给出 `PLG-0xx` + 解决指引 → ✅ **伪造 3 次启动失败 → 隔离 14 个第三方 bundle → 强杀重启后全恢复（闭环实测）**
- 渲染崩溃 5 秒内自动恢复（限次内）→ ✅ **RENDER-001 → 5s 自动 reload，节流/判环限次（brain-logic 26 项单测 + 代码路径实测）**
- 新插件安装出错不再白屏/空壳 → ✅ **pnpm 直连无 shell + friendlyPnpmError 中文指引 + 错误码 NPM-xxx**
- 打包坏包被冒烟当场拦截 → ✅ **BOM 坏包反测：冒烟 FAIL + exit 1 + 提示恢复备份；正常包 PASS**
- main.js 拆分后各模块独立可读、错误定位一行命中 → ✅ **main.js 2139 → 670 行（-69%），12 个 lib 模块，错误日志 JSON 行含 code/title/hint/msg/ctx**
