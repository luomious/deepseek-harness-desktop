# DSH 变更执行机制 — 安全隔离(方法 A)与先移植后覆盖(方法 B)

> **原则**: 任何可能影响系统稳定性的变更,**禁止直接改原位置**。
> 先隔离执行或先移植验证,成功才落地;失败零损伤、可回滚。
> 本机制为通用规则,本仓库一切高风险操作按此执行。

---

## 方法 A — 安全隔离机制(隔离 → 执行 → 验证 → 合并)

**适用**: 修改现有配置 / 增量装配(profile bundles、patch 补丁、依赖安装、配置文件改动)

```
判断 → 隔离 → 执行 → 验证 → 合并 →(失败)回滚
```

| 环节 | 动作 |
|---|---|
| 判断 | 目标是否影响启动/运行?是 → 必须走 A;只读/备份 → 直接执行 |
| 隔离 | 复制原位置到 staging(**排除 node_modules 等可重建目录**,pnpm 秒级重建) |
| 执行 | staging 内应用变更 + 依赖安装(原位置全程零改动) |
| 验证 | 组合检查(`dsh --profile <staging> --dump-config` 批次标记全出现)|
| 合并 | 备份原位置 → staging 三件套原子替换 → **原位置补装依赖** → 清理 staging |
| 回滚 | 任意环节失败 → 原位置未动,或从 `_backups` 恢复三件套 |

**参考实现**: `scripts/staged-profile-assemble.ps1`(批次 1-5,含 `-ValidateOnly` / `-Direct` 模式)

**已被该机制防住的真实故障**:
1. 合并漏 node_modules → `PackageOverlayNotFoundError`(应用起不来)——已修:合并后 desktop 补 `pnpm install`;
2. 合并漏本地 tgz(mcp-lens)→ `ENOENT`——已修:合并步骤带本地 file: 产物。

## 方法 B — 先移植后覆盖(移植 → 运行验证 → 成功覆盖 / 失败回滚)

**适用**: 整体替换型变更(运行时切换、exe 升级、vendor 换代)——"新的先上岗,旧的待命"。
新旧共用同一资源(如同一 profile / 同一端口语义)无法并存时,必须走 B。

```
判断 → 移植 → 验证 → 成功: 覆盖(旧物退役) / 失败: 回滚(旧物原样)
```

| 环节 | 动作 |
|---|---|
| 判断 | 替换的是"整体/运行时"且新旧无法并存 → 走 B |
| 移植 | 停旧 → 启新(新物接管原数据位) |
| 验证 | 进程存活 + 端口 HTTP 200 + **日志无新错误** + `startup.run.completed / healthy` |
| 成功 → 覆盖 | 新物成为唯一运行;旧物移入 `_backups\retired-*` 退役(可保留待命期再删) |
| 失败 → 回滚 | 停新 → 启旧(旧物从未被删除,秒级恢复) |

**参考实现**: `scripts/switch-runtime.ps1`

**已知实例**: Phase 2.5 —— 官方 `E:\DSH\DSH Desktop` → 自建 `dist\win-unpacked\DSH Desktop.exe`(同一 desktop profile,无法并存,走 B 完成切换并验证通过)。

## 判断规则(动手前先判断)

| 变更类型 | 方法 | 说明 |
|---|---|---|
| 只读预检 / 备份 / 仓库源码(git 可回滚) | **直接执行** | 无隔离必要 |
| 修改配置 / 增量装配 / 装依赖 | **A 隔离** | 原位置全程不被触碰 |
| 替换运行时 / 整体组件 | **B 移植** | 新物先验证,旧物待命 |
| 紧急救援(原位置已坏,须直改) | **A -Direct** | 显式跳过隔离,仍先备份 |

## 通用守则

1. **每步留痕**: 备份 + 记录到 `docs/升级执行记录.md`;
2. **验证可证伪**: dump-config 标记 / 健康检查 / 日志无新错误,缺一不放行;
3. **回滚可执行**: 备份存在、旧物未删,回滚动作必须是一两条命令能完成的;
4. **PS 5.1 铁律**: 含中文的 .ps1 必须 UTF-8 **带 BOM**(否则按 GBK 解析报语法错);edit 工具会去 BOM,改完需重加;
5. **环境限制**: 需子进程/管道能力的命令(构建、pnpm 原生构建)必须在 PTY 终端运行,harness shell 会 EPERM。
