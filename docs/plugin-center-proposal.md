# 插件中心方案书

> 目标：借鉴 `fufankeji/deepseek-harness-studio` 的「插件发现 / 热点推送 / 一键安装 / AI 智能推荐 / 视觉增强」能力，
> 在现有 **DeepSeek Harness Desktop**（Electron 薄封装 + 全局 dsh）架构上，以**不引入上游源码、不破坏现有鲁棒性工程**为前提，补齐产品体验层。
> 方案版本：v1（2026-08-20）

---

## 1. 背景与差距

当前项目（`D:\Deepseek-Harness`）已具备**扎实的底层插件管理能力**（`src/lib/plugin-manager.js`）：

- 用 `node + pnpm.cjs` 直连安装/卸载，**无 shell、零注入面**；
- 启用/禁用（写 `cordis.patch.yml`）、`reconcilePlugins` 对齐 bundle 层与纯前端挂载块；
- `validateArg` 包名/路径白名单、`friendlyPnpmError` 友好报错。

但**产品体验层缺失**：用户必须**事先知道精确的 npm 包名**才能安装插件，没有「浏览/发现」能力，也没有热点推荐与 AI 推荐。

对方 `fufankeji/deepseek-harness-studio` 的差异点正是：**插件中心（发现 + 热点 + AI 推荐）+ 视觉增强 + macOS**。
其中「插件发现 / 热点推送 / AI 推荐」可独立落地，且与我们的 wrapper 形态兼容；「深度 fork / vendored Cordis」与「macOS」则与现有策略冲突或优先级低，**不纳入**。

## 2. 总体设计

```
┌───────────────────────────────────────────────────────────────┐
│ 插件管理窗口（data: URL，CSP default-src 'none'）              │
│  已安装 / 远程 / 本地 / 【发现插件】  ← 新增标签页              │
│  渲染层只做 IPC + 展示 + esc 转义，不发网络                     │
└───────────────────────────┬───────────────────────────────────┘
                            │ electronAPI.listCatalog(query)
                            ▼
┌───────────────────────────────────────────────────────────────┐
│ 主进程 src/lib/plugin-catalog.js  ← 新增数据层                 │
│  · HTTPS-only + 重定向≤5 + 15s 超时 + 2MB 上限 + JSON 守卫      │
│  · 数据源：npm registry 搜索 API（keywords:dsh-plugin）        │
│  · 归一化 + 人气/近期排序 + 内存缓存(TTL) + 优雅降级(返回[])    │
│  · 任何异常都不向上抛（绝不崩）                                  │
└───────────────────────────┬───────────────────────────────────┘
                            │ 复用
                            ▼
┌───────────────────────────────────────────────────────────────┐
│ 现有 src/lib/plugin-manager.js installPlugin()                │
│  · validateArg('pkg') 白名单 → pnpm.cjs 无 shell → reconcile   │
└───────────────────────────────────────────────────────────────┘
```

**关键安全约束（沿用既有基线，不削弱）**：

1. 网络请求只在**主进程**发生（渲染层 CSP `default-src 'none'`，不放开 `connect-src`）。
2. 目录数据来自远程，**不可信**：渲染层展示前一律 `esc()` 转义；安装时包名再经 `validateArg('pkg')` 白名单二次拦截。
3. 新增 IPC `plugin:catalog` 为只读，且同样限制 `isPluginManagerSender`（仅插件管理窗口可调）。
4. 目录拉取**任何失败都降级为「目录暂不可用」提示**，不影响「远程/本地/已安装」现有能力（可手动输入包名兜底）。

## 3. 分阶段计划

### 阶段 1 —— 插件发现/目录（MVP，本次落地）
- 新增 `src/lib/plugin-catalog.js`（数据层，依赖注入 `fetchJson` 便于单测）。
- 新增 IPC `plugin:catalog` + `preload.listCatalog()`。
- 插件管理窗口新增「发现插件」标签页：搜索框 + 插件列表（名称/描述/版本/更新时间/人气）+ 每项「安装」按钮 + 已安装标记 + 优雅降级提示。
- 新增错误码 `PLG-004`（目录拉取失败）。
- 交付验收：断网/接口异常时不崩、提示友好、仍可手动装；正常时能浏览并一键安装。

### 阶段 2 —— 热点推送 + 规则版推荐
- 热点：目录按人气（`score.final`）排序，出「热门插件」区块。
- 规则版推荐：基于已装插件做类别协同（如装了 web-search → 推荐 web-fetch/routing），零 API 成本。

### 阶段 3 —— AI 智能推荐
- 复用 `~/.dsh/settings.yaml` 已有 provider/model，把「已装插件 + 用户需求」发给模型，返回候选包名，再走现有安全安装流程。

### 阶段 4 —— 视觉增强主题入口 + macOS（可选）
- 主题：把现有皮肤包纳入目录「主题」分类，提供「立即换肤」（本质是 bundle 安装 + reconcile）。
- macOS：评估用户群后决定，涉及窗口/托盘/打包改造。

### 阶段 5 —— 文档与分发
- 更新 PROJECT_README.md / CHANGELOG.md；补架构图。

## 4. 「不崩溃」保障策略

每个阶段落地后，按以下清单验证：

1. **语法**：`node --check` 逐文件。
2. **单测**：`tests/plugin-catalog.js` 注入 fake `fetchJson`，覆盖：正常归一化、人气排序、网络异常返回 `[]`、超时、非法 JSON、重定向降级、超大响应截断、缓存命中。全部断言「不抛错」。
3. **渲染层审查**：新增内联 JS 走 `esc()` 转义 + 事件委托（插件名不进内联 `onclick`），包名安装前白名单二次校验。
4. **降级兜底**：目录接口失败时，「发现」标签页显示可读提示，**不弹错误框、不阻塞**，其余标签页功能不受影响。
5. **真实启动**（可选）：改 `src/` 后按规范 `build-app.ps1` 重打 asar + 完全退出旧 exe 再启动验证（本次会话内可先用 `node --check` + 单测代替，真实 exe 验证需在系统终端执行）。

## 5. 风险与决策记录

| 风险/决策 | 结论 |
|---|---|
| 是否 vendor 上游源码（像 studio 一样） | **否**。与「全局 npm 安装 + patch-manifest 自愈」策略冲突，维护成本高 |
| 目录数据源用第三方社区站还是 npm registry | **npm registry**（官方、HTTPS、已在 update-check.js 验证过同款模式） |
| 是否放开渲染层 `connect-src` | **否**。保持网络请求在主进程，渲染层零联网 |
| 目录数据不可信（恶意描述/包名） | 展示前 `esc()` 转义 + 安装前 `validateArg('pkg')` 白名单，双层防御 |
| 是否实现 macOS | 暂缓，先做 Windows 价值闭环 |
