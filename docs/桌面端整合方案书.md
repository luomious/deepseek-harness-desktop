# DeepSeek Harness 桌面端整合方案书

**项目**：D:\Deepseek-Harness（DeepSeek Harness 桌面应用 + 插件生态）
**目标**：吸收 DSH Desktop 新壳（dsh-plugin-desktop v2.0.2）的全部稳定性能力，根治崩溃与 bug，保留并预置全部自研插件，最终形成"单仓库、单实例、开箱即用、可复现构建"的桌面应用。
**编制日期**：2026-08-22
**状态**：评估完成，待评审后分阶段执行

---

## 1. 项目背景

用户长期维护 `D:\Deepseek-Harness`（git: luomious/deepseek-harness-desktop），它由两部分组成：

1. **旧桌面壳**：`src/main.js` + `src/lib/*`（spawn 子进程拉起 `dsh web`、brain 自愈、safe-mode、patch-manifest 补丁、插件管理窗口、更新兼容、图标守护）。
2. **插件生态**：`plugins/` 下 20+ 个自研 DSH 插件（modlens 全家、模型路由、会话守护、技能管理、远程工作区、文件浏览器等）。

与此同时，官方/社区已发布**新一代桌面壳** `dsh-plugin-desktop` v2.0.2（npm 包，Electron 主进程即插件本体，进程内 boot DSH，自带全套稳定性设施），本机已安装并验证可运行（`E:\DSH\DSH Desktop`）。

**用户诉求**：两者"差不多"，希望把新壳的优点合并进 `D:\Deepseek-Harness`，重点是**防止项目崩溃和出 bug**，并评估风险与可行性。

## 2. 现状与问题诊断（基于实测证据）

### 2.1 双壳架构现状

| 项 | 旧壳（D:\Deepseek-Harness\src） | 新壳（dsh-plugin-desktop 2.0.2） |
|---|---|---|
| 架构 | 独立 Electron 主进程，`spawn` 子进程跑 `dsh web` | 本身就是 DSH Cordis 插件，进程内 `boot()` |
| profile | 固定 web profile | 默认 desktop profile，支持多 profile 管理 |
| 插件加载 | web profile bundles + super-injector 注入 | desktop profile（目前无自研插件） |
| 稳定性设施 | brain/safe-mode/patch-manifest（崩溃后补救型） | install-recovery 事务、健康检查点、Crashpad、启动链路日志（预防型） |
| 依赖 | 全局 @deepseek-ai/dsh + profiles 共享 node_modules | 自带 bundled node_modules（离线可跑）+ overlay 解析 |

### 2.2 崩溃/bug 根因（按证据排序）

1. **多实例并发写 `~/.dsh`（实证，正在发生）**
   - 实测：旧壳托管的 web 服务监听 `127.0.0.1:3080`，新桌面端服务监听 `127.0.0.1:43120`（3080 被占自动换端口），**两个 DSH 实例同时运行**。
   - 两个进程共享 `~/.dsh` 的 sessions（JSONL）、storages、settings、super-injector 全局注册表 → 并发写会话与状态文件 → 竞态、文件损坏、"各种奇怪问题"。
2. **自研插件的代码级崩溃点（4 🔴 + 3 🟡，均已定位到行号）**
   - 🔴 `dsh-remote-workspace/src/index.ts:254-275` run()：子进程三流无 `error` 监听，docker/ssh/wsl 缺失即进程级崩溃。
   - 🔴 `dsh-session-watchdog/src/index.ts:163`：`goals.resume()` 未 await 未 catch → 未处理 rejection。
   - 🔴 `dsh-context-lifecycle/src/index.ts:362-373`：pendingTimer 回调整体无 try-catch；`void runCompact()` 无 catch。
   - 🔴 `dsh-stuck-loop-guard/src/index.ts:258-280`：async 监听器 `await next()` 及下游处理在 try 外。
   - 🟡 `dsh-vision-engine/lib/client.js:744-749`：900ms 永久轮询 + 全局监听不清理（热重载累积）。
   - 🟡 `dsh-project-brief/src/index.ts:42`：writeFileSync 无 try/catch；fileName 未约束 `../`。
   - 🟡 `dsh-remote-workspace`：HTTP 响应写出（:731-732）、systemPrompt 回调（:672-680）、ctx.effect（:692）无兜底。
3. **旧壳架构性缺陷（崩溃的历史根源）**
   - spawn 子进程 + 自写端口自愈/进程管理 → 生命周期复杂易碎。
   - patch-manifest 直接改写 node_modules 里的客户端 bundle → 升级/重装极易出问题。
   - brain/safe-mode 属"崩溃后猜测式恢复"，不是预防。
4. **UI 差异根因（"不好看"）**
   - 实测 3080 页面（web profile）带 maid-atelier 皮肤、better-sidebar 等全套客户端插件；43120 页面（desktop profile）为素颜默认 UI。**缺插件，不是壳的问题。**

### 2.3 风险前提

- 本方案成立的前提：**先收敛单实例**（否则任何修复都敌不过并发写损坏）。
- 插件崩溃点必须**先修再搬**，否则等于把问题搬进新壳。

## 3. 目标与验收标准

### 3.1 目标

1. `D:\Deepseek-Harness` 成为唯一项目仓库：插件源码 + 新壳（vendor）+ 构建配方。
2. 桌面应用 = 新壳稳定性能力 + 全部自研插件，开箱即用。
3. 崩溃与 bug 从"补救型自愈"转为"预防 + 可诊断"（Crashpad/健康检查点/事务回滚）。
4. 单实例运行，杜绝多实例并发写 `~/.dsh`。

### 3.2 验收标准

| 编号 | 验收项 | 判定 |
|---|---|---|
| A1 | 单实例 | 任务管理器只有一个 DSH 应用进程组；无 `DeepSeek Harness.exe` 旧壳进程 |
| A2 | 功能完整 | 皮肤/侧栏/模型选择器/MCP/技能管理/文件浏览器/远程工作区/守护插件在桌面端出现且可用 |
| A3 | 稳定运行 | 连续 72h 无进程退出；`%APPDATA%\DSH Desktop\Crashpad` 无 dump；启动链路日志全绿 |
| A4 | 构建可复现 | 一条命令出包；产物复制到干净机器（或全新用户目录）可运行 |
| A5 | 无安装感（可选增强） | 首次启动自动装配 profile，无需手动 `pnpm add` |

## 4. 总体方案

### 4.1 架构设计

```
运行时（单实例）：
  DSH Desktop.exe（新壳，进程内 boot）
    └── boot ~/.dsh/profiles/desktop
          ├── dsh-base + dsh-web-app（核心）
          ├── desktop-*（壳能力：tray/终端/诊断/通知/更新/多profile/pnpm）
          └── 自研插件（bundles + patch 行 + super-injector，来自 D:\Deepseek-Harness）
```

仓库结构（目标态）：

```
D:\Deepseek-Harness\
├── plugins/                     # 20+ 自研插件源码（仅修崩溃点，结构不动）
├── dsh-context-lifecycle/       # 守护插件
├── dsh-stuck-loop-guard/        # 守护插件
├── vendor/dsh-plugin-desktop/   # 新壳完整包（复制本地 2.0.2，含 bundled node_modules）
├── profile/desktop/             # desktop profile 模板（三件套：package.json/cordis.patch.yml/pnpm-workspace.yaml）
├── electron-builder.yml         # 构建配置（对照已装 exe 反推）
├── build-app.ps1                # v2：校验 → 组装 profile → electron-builder 出包
├── scripts/                     # 原有脚本保留（install-dsh-plugins.ps1 等迁移/适配）
├── src/ → legacy/               # 旧壳降级保留参考，不再参与构建
├── docs/                        # 方案书与发布说明
└── package.json                 # 根构建配方
```

### 4.2 关键技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 新壳引入方式 | **vendor 复制**（本地 2.0.2） | npm latest=2.0.0 落后于本地 2.0.2；vendor 连同 node_modules 快照锁定版本，离线可跑 |
| 插件加载 | **预置 desktop profile 模板**（bundles + patch 行） | 遵循 DSH 官方组合机制，桌面 UI 可禁用/回滚 |
| 崩溃点 | **先修后搬**（Phase 1 独立成阶段） | 避免把已知崩溃搬入新壳 |
| 旧壳 | 降级 `legacy/`，不再构建 | 功能已被新壳覆盖；保留代码供对照 |
| 更新通道 | 默认保留官方更新；发布自管版本时改为自托管或关闭（待定） | 避免用户被官方版本覆盖而丢失预置插件 |
| 单实例 | 依赖新壳单实例语义（active-run.json） | 不再需要旧壳的自写端口/进程管理 |

### 4.3 核心文件清单（Phase 2/3 交付物）

1. `vendor/dsh-plugin-desktop/`（整包复制）
2. `electron-builder.yml`
3. `profile/desktop/package.json`、`profile/desktop/cordis.patch.yml`、`profile/desktop/pnpm-workspace.yaml`
4. `build-app.ps1`（v2）
5. 根 `package.json`（构建配方）

## 5. 分阶段实施计划

### Phase 0：环境收敛与备份（5 分钟）

1. 退出旧壳 `DeepSeek Harness.exe`（任务管理器结束全部 4 个进程）与独立 `dsh web` 进程；只保留 `DSH Desktop.exe`。
   - ⚠️ 此操作会断开当前 3080 网页会话。
2. 备份（PowerShell）：
   ```powershell
   $p = "$env:USERPROFILE\.dsh\profiles\desktop"
   Copy-Item "$p\package.json" "$p\package.json.bak-$(Get-Date -Format yyyyMMdd-HHmmss)"
   Copy-Item "$p\cordis.patch.yml" "$p\cordis.patch.yml.bak-$(Get-Date -Format yyyyMMdd-HHmmss)"
   Copy-Item "$p\pnpm-workspace.yaml" "$p\pnpm-workspace.yaml.bak-$(Get-Date -Format yyyyMMdd-HHmmss)"
   Copy-Item "$env:USERPROFILE\.dsh\profiles\web\package.json" "$env:USERPROFILE\.dsh\profiles\web\package.json.bak-$(Get-Date -Format yyyyMMdd-HHmmss)"
   ```
3. 记录现状快照：`netstat -ano | findstr 3080` 应无监听。

**产出**：单实例环境 + 可回滚备份。

### Phase 1：插件崩溃点修复（约半天）

原则：**同时改 `src/` 与 `lib/`**（运行时加载 lib，src 为后续重建源），改完重新构建并冒烟测试。

| # | 插件 | 位置 | 修复内容 |
|---|---|---|---|
| 1 | dsh-remote-workspace | `src/index.ts` run() | child 及 stdout/stderr/stdin 各挂 `on('error', () => {})`；spawn 失败不再进程级崩溃 |
| 2 | dsh-session-watchdog | `src/index.ts` cycle() | `goals.resume` 改为 `await` 并包 try/catch（或 `Promise.resolve(...).catch(log)`） |
| 3 | dsh-context-lifecycle | `src/index.ts` | pendingTimer 回调整体 try-catch；`void runCompact(state).catch(log)` |
| 4 | dsh-stuck-loop-guard | `src/index.ts` | `await next()` 到 return 整段包 try-catch；`crypto` 改用 `node:crypto`；WeakMap key 先判对象；spawn 挂 error |
| 5 | dsh-vision-engine | `lib/client.js` + 客户端源码 | 900ms 轮询与全局监听移入 `ctx.effect` disposer |
| 6 | dsh-project-brief | `src/index.ts` | writeFileSync 包 try/catch；fileName 拒绝 `..` |
| 7 | dsh-remote-workspace | `src/index.ts` | HTTP 响应写出、systemPrompt 回调、ctx.effect 均包 try/catch |

构建命令（按插件）：`bash scripts/build.sh`（Git Bash）或 `npx tsc -p tsconfig.json && npx tsdown`（按各自 package.json scripts）。
冒烟：每个插件 `node --check` 语法 + 在 web profile 下加载 10 分钟无未捕获异常。

**产出**：加固后的插件源码 + lib，重新构建产物。

### Phase 2：新壳并入与构建（2~4 小时）

1. vendor 复制：
   ```powershell
   Copy-Item "$env:USERPROFILE\.dsh\profiles\node_modules\dsh-plugin-desktop" "D:\Deepseek-Harness\vendor\dsh-plugin-desktop" -Recurse
   ```
2. 重建 `electron-builder.yml`（对照 `E:\DSH\DSH Desktop` 反推，要点）：
   ```yaml
   appId: com.dsh.desktop
   productName: DSH Desktop
   directories:
     output: app
   files:
     - vendor/dsh-plugin-desktop/**/*   # 或直接以 vendor 目录为 app dir
   asarUnpack:
     - node_modules/**                  # 原生模块全部解包（与现 exe 的 asar 结构一致）
   win:
     target:
       - nsis
       - portable
     icon: build/app-icon.png
   nsis:
     oneClick: true
     perMachine: false
     allowToChangeInstallationDirectory: false
     deleteAppDataOnUninstall: false
   electronVersion: 43.4.0
   publish: null                        # 默认关闭；自托管时改 github/自定义端点
   ```
   （appId/产品名可按用户品牌调整；NSIS 参数以 `--updated --force-run` 更新协议为准。）
3. 首次试包：`npx electron-builder --win nsis`，与已装 exe 对照 `app.asar` 结构（全部 unpacked）、`elevate.exe`、卸载器存在。
4. 根 `package.json` 构建配方：`devDependencies: electron@43.4.0, electron-builder`，`scripts.build`。

**产出**：与官方新壳一致的本地构建 exe。

### Phase 3：预置 profile 模板（1 小时）

1. 将第 3.1/3.2/3.3 节的三件套写入 `profile/desktop/`（bundles = dsh-base + dsh-web-app + 21 个自研 bundle；cordis.patch.yml = 6 个非 bundle 插件 insert + super-injector `profileNodeModules` 覆盖；pnpm-workspace.yaml = allowBuilds/minimumReleaseAgeExclude）。
2. `build-app.ps1` v2 流程：语法检查 → 复制 `profile/desktop` 到 `~/.dsh/profiles/desktop`（首次/重置）→ `pnpm install --dir profile/desktop` → 预检 `dsh --profile desktop --dump-config` → electron-builder 出包。
3. 本机全量验证：卸载/停用旧壳 → 运行新 exe → 按 3.5 验证清单逐项确认。

**产出**：带全部插件的可分发 exe + 一键构建脚本。

### Phase 4：验证与稳定观察（3~5 天）

1. 按第 3.2 节验收清单逐项过。
2. 监控：`%APPDATA%\DSH Desktop\logs\*.log`、`lifecycle-events\startup.jsonl`、`Crashpad\`、`health-snapshots\`。
3. 复测插件冒烟：模型路由升降级、modlens 读图、远程工作区（含 docker/ssh 缺失场景）、技能管理、文件浏览器。
4. 记录问题并回填本方案书（变更记录）。

**产出**：稳定结论 + 已知问题清单。

### Phase 5（可选增强）：开箱即用 / 无安装感

- 在 vendored 新壳内增加"首次启动 seed profile"逻辑：检测 `~/.dsh/profiles/desktop` 缺失或非模板版本时，从包内 `profile/desktop` 模板物化 + 触发一次 pnpm 安装（复用 desktop-pnpm 运行时），实现 A5 验收项。
- 自托管更新端点（或关闭更新），避免官方更新覆盖预置 profile。

## 6. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| electron-builder 配置重建不完整 | 中 | 以已装 exe 为对照物反推；预留 1~2 次试包；产物对比 asar 头结构与文件列表 |
| 插件在新壳下兼容性未知 | 中 | Phase 3 全量验证清单；冲突 bundle 在 profile 层禁用；皮肤冲突禁用其一 |
| 新壳升级漂移（dsh 版本、shell 版本） | 中 | vendor 整包锁版本；升级走"重新 vendor + 回归"流程 |
| 崩溃点修复引入新问题 | 低-中 | 每插件独立提交 + 冒烟；改动最小化（只加防护不加逻辑） |
| 多实例复发（用户又开旧壳/web） | 低 | Phase 0 明确退役旧壳；文档明示单实例纪律；必要时旧壳入口改名 |
| 更新通道覆盖预置 profile | 中 | Phase 2 默认 `publish: null`；自托管后启用 |
| **不做本方案** | **高** | spawn + patch-manifest + 多实例问题持续存在，崩溃无法根治 |
